## 2. 当前已知信息

### 2.1 已确认

- 项目名称暂定为 `Soft Energy Leaderboard`。
- 项目需要先完成需求梳理，再开始开发。
- 根目录下需要建立独立的开发文档目录。
- 开发文档后续可包含需求文档、开发文档、备忘录及其他必要资料。
- 产品基础形态是一个面向学生的“限时答题竞赛 + 自动判定 + 排行榜”系统。
- 老师或管理人员需要在管理栏目中录入考题及标准答案。
- 所有参与学生都可以看到考题，但不能看到预先录入的标准答案。
- 学生查看考题后，可以提交自己的答案。
- 系统按老师录入的两句标准答案进行精确判定；仅忽略表情符号，其余文字、字数、标点和顺序均参与比较。
- 去除表情后，两句内容与顺序均百分之百一致的答案进入“冠军”榜。
- 两句内容均完全正确、但上联与下联整体颠倒的答案进入“亚军”榜；部分正确不进入亚军榜。
- 完全错误的答案不进入冠军榜或亚军榜，但仍需保留答题记录，便于审计和统计。
- 每场答题有明确的有效时间段，默认从实际发布时间起12小时截止；管理员可改为24小时等整数小时，或直接指定开始与截止日期时间。
- 截止时间到达后，系统需要列出该场答题的冠军名单和亚军名单。
- 榜单需要让参与者清楚看出谁更早提交了有效答案，以及答案所属等级。
- 学生客户端确定采用微信小程序。
- 系统需要提供独立的 Web 管理后台，用于出题、统计用户、查看答题记录和排行榜。
- 当前管理后台只有管理员使用，首版只需要一个默认管理员账号，不建设多角色、多权限体系。
- 管理员账号与微信小程序用户账号相互独立，不进行账号绑定。
- 小程序需要支持微信登录；用户主动同意现行用户协议和隐私保护指引后，仅记录建立独立身份所需的 OpenID、用户自行设置的修习名及答题数据。首版不收集手机号、微信头像、位置、通讯录或相册。
- 小程序登录后需要展示当前用户的个人资料和个人答题数据。
- 管理后台需要统计小程序用户资料、参与情况和排名结果。
- 当前产品不涉及支付、订单、会员、收费或其他盈利功能。
- 每位小程序用户的个人资料、答题记录、判定结果和排名必须稳定关联，不得发生用户数据串联或混乱。
- 产品内容以东方哲学和国学为主要文化基础，核心涉及儒家、佛教与道家思想。
- 产品内容来源于师父在儒、释、道修习基础上的理解、融合与创新，最终表达不应简单等同于传统经典原文。
- 师父现年约 80 岁，是核心内容和思想体系的重要来源；内容录入可由管理员完成，师父不一定直接操作管理后台。
- 小程序核心用户为 30 岁以上人群，当前重点考虑约 35—60 岁用户，其中中高龄用户占比较高。
- UI 需要具有当代国学与东方美学气质，同时保持简单、顺滑、易读，不能做成陈旧仿古网页或廉价国风模板。
- 技术栈已冻结为：微信原生小程序 + TypeScript + TDesign Miniprogram；Vue 3 + TypeScript + Vite + Element Plus 管理后台；Java 21 + Spring Boot 3.5.16 后端；MySQL 8.4 LTS 数据库。
- 首版不使用 Python/FastAPI、Node.js/NestJS、UniApp、React、SQLite、MongoDB、Redis、微服务或独立 AI 判题服务。
- 项目必须按企业级工程标准实施，包括数据库迁移、自动化测试、接口版本、统一错误码、日志追踪、健康检查、安全审计、依赖锁定、持续集成和可恢复发布。
- UI 必须达到现代、丝滑、商业化和适龄要求，组件库默认样式不能直接作为最终界面。
- 正式服务器固定使用阿里云：一台 ECS 承载 Jenkins、Nginx 和 Java 服务，生产数据库使用同地域、同 VPC 的阿里云 RDS MySQL 8.4 高可用系列。
- 正式发布固定使用 Jenkins Pipeline；Java 服务由 systemd 托管，Vue 管理后台由 Nginx 静态托管，Nginx 统一提供 HTTPS 并反向代理 `/api/v1`。
- 生产应用不使用 Docker Compose，也不在 ECS 自建生产 MySQL；Docker 仅用于开发电脑上的 MySQL 8.4 本地环境。
- 服务端和管理后台使用版本化目录原子发布，健康检查失败自动恢复上一应用版本；数据库迁移只允许 Flyway 向前、兼容式变更，不能依赖自动降级 SQL。
- 小程序由 Jenkins 完成类型检查、测试、构建校验和开发版本上传；体验版验证、提交微信审核和正式发布必须由管理员人工确认。
- 源码仓库固定使用 GitHub 组织下的私有仓库 `soft-energy-leaderboard`，使用 GitHub Team 的仓库规则保护 `main` 和正式版本标签，不再使用 GitLab、Gitee 或自建 Git 服务。
- GitHub 负责源码、Issue、Pull Request、里程碑和 Release 记录；Jenkins 负责 CI/CD，不重复建设 GitHub Actions 发布流水线。
- 小程序和管理后台正式页面必须设计先行：先完成视觉研究、统一 Token、核心线框和高保真基线，再固化为页面与业务组件；不得用 TDesign、Element Plus 或后台模板的默认布局和默认主题应付交付。
- “只替换组件库主色”“堆叠默认卡片”“套用通用后台侧栏和登录页”均不视为完成 UI 设计，必须按《UI 设计规范》的返工条件重新设计。
- 产品采用“管理端先完成全业务验收、业务规则冻结后再集中完成小程序”的交付策略；不把微信审核版本作为日常试错环境。
- 管理端测试中心必须复用正式后端题目、作答、判定、排名和统计链路，用于在小程序提审前验证完整业务。
- 小程序定位为正式用户的轻客户端：负责微信身份、题目展示、作答、结果、榜单、个人档案、隐私与异常反馈，不在前端复制判题或排序规则。
- 首次提审前必须一次性完成 UI、真机联调、隐私保护指引、用户协议、数据管理入口、内容安全和审核资料；达到发布门禁后才允许上传审核版本。
- 首版答题不以手机号授权为前置条件。手机号当前无不可替代的业务用途，因此首个正式版本不主动收集；后端加密能力保留，未来确需启用时必须重新评估用途、告知、授权和隐私声明。

### 2.3 产品文化定位

产品不是传统应试教育题库，也不是单纯以胜负为目的的排行榜。其核心价值是：

1. 将师父基于儒、释、道形成的思想内容转化为适合移动端传播和参与的问答形式；
2. 通过作答帮助用户理解、回顾和实践相关思想，而不是只记忆标准文字；
3. 通过冠军榜、亚军榜和提交时间形成适度激励，但不制造焦虑或对用户人格、修行境界作绝对评价；
4. 逐步沉淀为具有自身方法体系的“东方软能力修习平台”。

内容表达需要区分：

- 儒家经典及相关思想；
- 佛教经典、释义及相关思想；
- 道家、道教经典及相关思想；
- 师父的原创理解、融合观点和实践方法；
- 管理员或编辑为小程序整理的题目、解析与答案规则。

不同来源不能混写成同一种权威口径。每条内容后续应记录分类、出处、原文、师父讲解、编辑说明和版本，避免文化概念混乱或无法追溯。

### 2.1 首个正式版本的合规边界

长期内容愿景不等于首版可公开发布范围。首个正式版本统一以“中华传统文化与经典哲思学习答题”对外呈现，只开放经典阅读、经典哲思、生活实践和传统文化分类。在运营主体取得主管部门书面确认与适用资质前，佛教、道教、宗教教义、宗教教育、讲经讲道、师门传法、修炼指导、宗教仪式、招生和募捐内容不得进入公开题库；后台应阻止相关分类发布，历史待确认分类不得由小程序公开接口返回。

首版新增完整投诉治理：用户可以举报题目和榜单昵称、提交侵权投诉、评分申诉和隐私请求；管理员可以处理、回复、重置违规昵称或停用账号。账号注销时必须删除身份、原始答案和可关联记录，只允许保留无法跨活动关联的单场匿名荣誉快照。

## 3. 产品机制概览

一场答题活动的基础流程如下：

1. 老师创建一场答题活动。
2. 老师录入考题、按上联/下联顺序分两行填写标准答案，并选择按时长或指定日期时间截止。
3. 活动开始后，学生看到考题，但看不到标准答案。
4. 学生在有效时间内填写并提交答案。
5. 系统记录提交人、提交内容和准确到秒的提交时间。
6. 系统将学生答案与标准答案进行自动比对。
7. 去除表情后逐字逐句且顺序完全一致者进入冠军榜；仅上下联整体颠倒者进入亚军榜；其他答案不入榜。
8. 系统向学生返回本次答题结果，具体反馈内容待确认。
9. 截止时间到达后停止有效排名，生成并公开最终冠军榜和亚军榜。
10. 同一等级内原则上按照有效提交时间从早到晚排列，最终排序口径待确认。

## 4. 产品目标

### 4.1 核心目标（待确认）

建立一套能够承载师父原创思想体系和儒、释、道文化内容的移动修习问答平台，让管理员可以快速发布内容，用户可以限时作答，系统可以自动判定并按正确程度和答题速度形成适度激励。

### 4.2 业务结果（待确认）

- 老师能够方便地录入题目、标准答案和答题时间。
- 学生只能看到题目，不能提前看到标准答案。
- 系统能够自动完成基本判定，减少老师人工批改和统计名单的工作量。
- 排名同时体现答案质量和提交速度，而不是只形成一张静态名单。
- 截止后所有参与者能够快速看懂冠军、亚军及各自排序。
- 页面和交互达到真实商业产品标准，适合正式对外使用。
- 文化表达庄重、准确、克制，让 30—60 岁用户愿意长期阅读和参与。
- 用户使用时感受到的是“温润、清明、有秩序”，而不是考试压力、宗教符号堆砌或娱乐化竞争。

### 4.3 成功指标（待补充）

- 看到题目的学生人数与实际答题人数。
- 有效时间内的答题参与率和提交完成率。
- 系统自动判定结果与老师人工复核结果的一致率。
- 每场活动冠军、亚军和未入榜人数。
- 老师发布题目、统计结果所需时间的下降幅度。

## 6. 核心使用场景

### 6.1 老师发布考题

老师在管理栏目中填写题目和标准答案，设置答题开始时间、截止时间及判定规则，然后发布活动。标准答案只用于系统判定，学生端不得返回或泄露该字段。

### 6.2 学生查看并提交答案

学生进入活动后查看题目，在有效时间内填写答案并提交。系统必须记录学生身份、原始答案和提交时间。

### 6.3 系统自动判定

系统将学生答案与标准答案进行对比，将结果分为冠军、亚军或不入榜，并向学生反馈本次结果。判定规则需要支持对“内容正确但顺序错误”的答案进行识别。

### 6.4 截止后公布排行榜

答题截止后，系统冻结最终排名并分别展示冠军榜与亚军榜。榜单需要显示名次、学生身份和提交时间，使参与者能够看出答题质量及先后顺序。

### 6.5 老师复核异常答案

自动判定存在争议时，老师应能查看学生原始答案、系统判定依据和提交时间，并进行人工复核。是否允许修改最终等级和排名待确认。

### 6.6 管理端模拟真实答题

在微信小程序完成审核前，管理员可以进入管理系统的“测试中心”，使用明确标注的测试学员身份查看已发布题目、提交答案、查看个人判定和截止后的榜单。测试中心不得建立独立的假数据或简化判题规则，其提交必须进入真实用户、答题记录和排行榜计算链路，并在管理端总览、学员档案和题目详情中同步可见。管理员身份与测试学员身份必须隔离，测试会话不得获得管理权限。正式对外开放前必须清理或隔离测试学员数据，测试身份不得污染真实用户的公开参与人数和最终榜单。

### 6.7 管理端先验收、小程序一次上架

1. 先在管理端完成题目草稿、发布、开放、作答、自动判定、重复提交、截止、揭榜、人工复核、学员统计和审计记录的完整验收。
2. 业务验收通过后冻结接口字段、判题规则、时间规则、错误码和榜单口径；此后小程序不再承担业务规则试错。
3. 小程序集中完成正式 UI、微信登录、用户展示名称、题目与作答、结果与榜单、个人中心、隐私管理、异常状态和真机适配。
4. 使用真实 AppID、HTTPS 域名和至少两个真实微信账号完成体验版验收，验证身份隔离、弱网重试、重复点击、截止边界和隐私拒绝场景。
5. 只有《小程序一次上架方案》中的发布门禁全部通过，才生成审核候选版本并提交。微信平台审核结果存在外部不确定性，目标是一次准备完整并显著减少返工，不对“绝对只审核一次”作不真实承诺。

### 6.8 两端统一测试账号

1. 后端集中提供10个固定中文测试账号，管理系统和小程序必须使用同一账号标识，不得各自维护两套默认账号。
2. 小程序测试中心仅在开发版显示；进入账号列表前必须使用管理员账号验证，管理员密码不得写入代码或持久化到本地。
3. 切换测试账号后，整个小程序以该学员的 USER 权限会话运行，题目、作答、评分、个人记录和榜单必须复用正式接口并写入同一数据库。
4. 管理系统切换到同名测试账号时，必须看到同一用户、同一提交和同一判定结果；管理员仍是唯一可以创建和发布题目的角色。
5. 体验版和正式版必须隐藏测试中心入口，并拒绝通过页面路径使用测试切换能力；生产发布不得迁移本地测试数据。

## 7. 首版功能范围（已确认）

### 7.1 学生端

1. 答题活动页
   - 展示活动名称、考题、开始时间、截止时间和剩余时间。
   - 不展示标准答案及其他仅限老师查看的判定信息。
   - 截止后禁止产生新的有效排名记录。

2. 答案提交
   - 学生输入并确认提交答案。
   - 记录原始答案、学生身份和服务器提交时间。
   - 防止重复点击造成多条重复提交记录。

3. 答题结果反馈
   - 告知学生本次答案属于冠军、亚军或未入榜。
   - 反馈是否展示标准答案、错误位置或修改机会，待确认。

4. 最终排行榜
   - 分别展示冠军榜和亚军榜。
   - 展示名次、学生名称或其他身份标识、有效提交时间。
   - 突出显示当前学生自己的结果和排名。

5. 微信登录与个人中心
   - 通过微信小程序登录建立系统用户身份。
   - 首版由用户设置用于榜单展示的“修习名”，明确告知其公开范围；头像采用文字头像，不强制收集微信头像。
   - 展示当前用户自己的修习名和答题统计，不展示或收集当前业务不需要的手机号。
   - 提供隐私保护指引、用户协议、个人信息清单、信息更正与账号注销入口。
   - 用户拒绝非必要授权时仍可浏览公开题目；提交答案前只要求完成维持身份与榜单所必需的最小授权。

6. 稳定性与状态反馈
   - 覆盖首次进入、未登录、加载中、空列表、无网络、接口失败、提交中、提交成功、重复点击、活动未开始和已截止状态。
   - 提交按钮必须防重复；请求失败时保留用户尚未提交成功的答案并提供明确重试入口。
   - 所有核心页面适配常见微信机型、安全区和系统字体缩放。

### 7.2 老师端/管理端

1. 创建、编辑和发布答题活动。
2. 录入题目和标准答案。
3. 配置开始时间、截止时间和判定规则。
4. 查看学生参与情况、原始答案、提交时间和自动判定结果。
5. 查看冠军榜、亚军榜及未入榜记录。
6. 对争议答案进行人工复核，并保留操作记录。
7. 结束、关闭或归档答题活动。
8. 查看小程序用户列表和用户详情。
9. 统计用户注册时间、最近登录时间、参与次数、冠军次数和亚军次数。
10. 首版使用一个独立默认管理员账号登录，不与任何小程序用户绑定。
11. 提供测试中心，支持创建和切换多个“测试学员”身份。
12. 测试学员按真实活动时间、作答次数、判题、答案揭晓和榜单规则完成作答。
13. 测试提交同步进入总览、学员档案、答题记录及冠军/亚军榜，并以“测试学员·名称”明确标识。
14. 上线前提供测试数据识别、隔离或清理机制，防止测试学员进入真实公开统计与榜单。
15. 管理员可修改初始化密码；生产环境禁止继续使用本地开发密码 `123456`。
16. 管理员处理用户举报、侵权投诉、评分申诉与隐私请求，并保留处理状态、回复和审计记录。
17. 管理员可对被举报昵称执行重置，对违规账号执行停用。
18. 管理员可删除从未发布的草稿题目；删除前必须二次确认并记录审计。题目一旦发布，或已经产生答题、榜单数据，不得删除。

### 7.3 暂不确定是否纳入首版

- 多道题组成一份试卷。
- 题库、随机抽题和批量导入题目。
- 分享榜单或生成个人成绩海报。
- 勋章、等级、连续签到和奖励兑换。
- 开始提醒、截止提醒和排名通知。
- 多组织、多班级或多租户管理。
- 成绩导入、导出及第三方教学系统对接。
- 多管理员、角色和细粒度权限管理。
- 支付、订单、会员和收费功能。

## 8. 核心业务规则

### 8.1 判定等级

| 等级 | 当前定义 | 是否进入榜单 |
| --- | --- | --- |
| 冠军 | 去除表情符号后，两句答案的文字、字数、标点和顺序与老师标准答案完全一致 | 进入冠军榜 |
| 亚军 | 去除表情符号后，两句文字各自完全正确，但上联、下联整体颠倒 | 进入亚军榜 |
| 未入榜 | 少字、多字、错字、标点不同、内容不完整或并非两句整体反转 | 不进入公开榜单，但后台保留记录 |

判定口径已冻结为确定性精确规则，不使用关键词覆盖率、亚军阈值或 AI 语义相似度。系统只移除 Unicode 表情序列并统一不同操作系统的换行符；其他内容不做宽松规范化。

### 8.2 排序规则

当前建议采用“先按等级分榜，再按首次达到该等级的有效提交时间升序排列”：

1. 冠军只与冠军排序，最早提交百分之百正确答案的学生排在前面。
2. 亚军只与亚军排序，最早提交上下联整体颠倒答案的学生排在前面；若无人发生该情况，亚军榜为空。
3. 提交时间以服务器记录为准，避免学生设备时间不准确或被修改。
4. 同一等级可以有多人，页面显示冠军1、冠军2或亚军1、亚军2；等级相同，仅先后编号不同。服务器内部保留高精度提交时刻，页面至少展示到秒。

### 8.3 活动时间

- 每场活动有明确的开始时间和截止时间，默认从题目实际发布时刻起开放12小时。
- 模式一为“发布后按时长截止”，管理员输入12、24等1至720之间的整数小时，系统从真实发布时间计算截止时刻。
- 模式二为“指定日期时间截止”，管理员直接选择开始日期时间与截止日期时间。
- 开始前不能提交答案；截止后提交不再进入有效排名。
- 截止时系统冻结最终结果，后续人工复核如何影响榜单待确认。

### 8.4 重复提交

是否允许学生在截止前多次提交尚未确定，需要从以下方案中选择：

1. 只允许提交一次，提交后不能修改；
2. 允许多次提交，以第一次提交结果和时间为准；
3. 允许多次提交，以第一次达到最高等级的时间作为排名时间；
4. 允许修改到截止时间，以最后一次提交作为最终答案。

从竞赛公平和鼓励快速答对的目标看，当前更建议采用第 3 种，但需要业务方最终确认。

### 8.5 答题后反馈

用户原描述中提到系统自动回复学生“正确答案”，这里存在关键歧义：

- 如果指“告诉学生本次答得是否正确”，可以即时反馈等级，但不必展示标准答案。
- 如果指“直接展示系统中的标准答案”，则可能被转发给尚未作答的学生，影响竞赛公平。

当前建议在活动进行中只反馈判定结果，不展示完整标准答案；活动截止后再决定是否公开标准答案和解析。最终方案待确认。

### 8.6 榜单公开时间

已确认截止时需要列出冠军榜和亚军榜。活动进行中是否实时展示榜单、只展示参与人数，还是完全隐藏排名，后续确认。

## 9. 页面与体验要求

- 页面视觉应高级、自然、商业化，符合企业 AI 咨询教育业务定位。
- 整体风格确定为“温润的新中式书院感”，以当代东方审美承载国学内容。
- 不直接照搬寺庙、道观、宫殿或古籍页面，不同时堆叠莲花、八卦、竹子、祥云、佛像等符号。
- 文化感主要通过留白、比例、字体层级、克制配色、纸张肌理和少量印章式点缀建立。
- 正文优先使用清晰的无衬线中文字体；宋体或现代中文衬线字体只用于标题和短句，不能大段使用影响阅读。
- 主要用户年龄偏大，默认正文字号、行距、点击区域和颜色对比度应高于普通年轻化小程序。
- 移动端优先，同时保证常见桌面端宽度下正常使用。
- 题目、剩余时间、提交状态、判定等级和个人排名应形成清晰的视觉层级。
- 核心按钮必须表达具体动作，例如“提交答案”“确认提交”“查看最终榜单”，避免含糊文案。
- 不堆砌渐变、光效、科技线条和无意义装饰。
- 前三名可以重点展示，但不能影响完整榜单的可读性。
- 活动未开始、进行中、已提交、已截止、未登录、未入榜和加载失败等状态均需提供明确反馈。
- 涉及排名竞争时，应考虑用户隐私及名称、头像的展示范围。
- 页面动效以 180—260ms 的淡入、位移和状态过渡为主，避免长时间水墨动画、飘动粒子或影响答题的装饰动画。
- 底部导航和主要按钮使用“图标 + 文字”，不让用户猜测图标含义。
- 提交答案、退出未保存内容、覆盖历史答案等高影响操作必须有清楚确认。

## 10. 非功能需求

### 10.1 性能

- 首屏应尽快展示排行榜骨架或主要内容。
- 参与人数较多时，榜单应采用分页、按需加载或虚拟列表等合适方案。
- 避免因频繁刷新排名导致页面闪动或名次错乱。
- 国风背景图和纹理需要压缩并按设备尺寸加载，不能因为视觉素材拖慢首屏。

### 10.2 适龄与无障碍

- 小程序默认正文建议不小于约 18px，题目正文建议约 20—22px，并提供“标准/大字”切换能力。
- 正文行高建议为字号的 1.6—1.75 倍，长题目按段落分隔。
- 普通可点击区域不小于约 44×44px，主要按钮建议达到 48—56px 高度。
- 普通正文与背景对比度目标不低于 4.5:1，不能使用浅灰小字表达关键内容。
- 倒计时同时提供完整文字，例如“距离截止还有 7 小时 32 分”，不能只显示颜色或圆环。
- 表单错误需要同时使用文字、图标和颜色提示，不能仅靠红色区分。
- 交互文案使用日常中文，不使用只有年轻用户熟悉的网络词或隐晦手势。

### 10.3 安全与数据可信度

- 标准答案不得出现在学生可访问的接口响应、网页源代码或前端状态中。
- 答案提交、自动判定和人工复核必须有完整记录。
- 人工调整需要记录操作人、时间、原因和调整前后等级。
- 学生不能通过修改前端参数伪造提交时间或判定结果。
- 涉及账号、手机号或组织信息时，应按最小必要原则展示。
- 微信用户以服务端通过微信登录流程取得的身份标识建立唯一关联，不能以前端提交的用户编号作为身份依据。
- 手机号属于个人信息，应加密存储、按需解密，并在管理列表中默认脱敏展示。
- 微信登录、手机号授权和昵称头像收集应分别处理，不把“登录成功”等同于“已授权全部个人信息”。
- 管理员账号使用独立数据表、独立登录接口和独立鉴权守卫，不与小程序用户表建立绑定关系。
- 学生提交答案时，后端必须从登录态取得当前用户 ID，接口不得信任前端自行传入的用户 ID。
- 用户、答题活动、提交记录和最终成绩之间必须使用数据库外键、唯一约束和事务保证关联一致性。
- 管理员密码不得明文存储，默认账号首次登录后必须修改初始化密码。

### 10.4 可维护性

- 活动时长、答案要点和判定规则应尽量配置化，避免频繁修改代码。
- 用户端与管理端使用一致的业务口径。
- 关键字段、接口和状态需要形成开发文档，便于后续接手。

## 11. 验收标准（草案）

首版至少应满足：

1. 老师能够创建活动并录入题目、标准答案、开始时间和截止时间。
2. 学生能够正常打开答题页，但无法通过学生端接口或页面代码获取标准答案。
3. 学生可以在有效时间内提交答案，系统正确记录学生身份、原始答案和服务器时间。
4. 系统能够按照最终确定的规则生成冠军、亚军和未入榜结果。
5. 冠军榜和亚军榜分别排序，同等级中较早有效提交者排列在前。
6. 活动截止后不能产生新的有效排名，最终榜单能够正常展示。
7. 当前学生能够快速找到自己的判定结果和排名；未入榜时有明确提示。
8. 重复提交、空答案、截止瞬间提交、网络重试和相同提交时间等边界情况有明确处理。
9. 老师可以查看原始答题记录并复核异常答案，操作过程可追踪。
10. 移动端和桌面端无明显布局错误，核心流程无控制台报错。
11. 管理员可在测试中心模拟至少两个独立学员，提交后能在题目答题记录和学员档案看到同一份结果。

## 12. 需要业务方优先补充的信息

后续描述需求时，可以自由表达，不要求按顺序回答。至少需要逐步明确以下内容：

1. 一场活动只有一道题，还是可能包含多道题？
2. 标准答案是固定文字、多个要点、多个步骤，还是可能包含图片和附件？
3. 是否还会出现不是“两句/上下联”结构的题型？当前首版判题已固定为两句精确答案。
4. 是否需要在未来增加不影响首版榜单的练习型、开放式主观题？
7. 学生提交后，是只告知判定等级，还是立刻展示完整标准答案？
8. 学生能否多次提交，排名采用哪一次答案和哪一个时间？
9. 活动进行中是否展示实时榜单，还是截止后统一公开？
10. 榜单展示学生真实姓名、昵称、头像还是脱敏信息？
11. 管理后台首版是否只面向电脑使用，还是也需要适配手机浏览器？
12. 是否已有班级或学员数据，需要与微信登录用户进行人工确认或关联？
13. 老师能否人工修改系统判定，修改后是否影响最终排名？
14. 首版预计多少学生同时参与，何时需要投入使用？
15. 是否需要奖励、证书、积分、通知、导出名单或分享功能？
16. 若未来新增必须依赖手机号的业务，具体用途、保存期限与拒绝后的替代流程是什么？首版已经确认不收集手机号。
17. 排行榜应该显示微信昵称、真实姓名还是管理员维护的学员名称？
18. 产品正式中文名称、师父思想体系名称和对外品牌名称分别是什么？
19. “学生”“用户”“学员”“修习者”中，产品正式采用哪一种称呼？
20. 儒、释、道和师父原创内容是否需要分栏目展示，还是只在后台分类？
21. 经典原文、现代释义和师父原创讲解分别由谁确认和审核？
22. 是否已有经过授权的书法、绘画、印章、师父照片或品牌素材？
23. 用户年龄结构中，50—60 岁用户预计占比多少，是否需要默认大字模式？

## 13. 当前不做的事项

- 不在开发过程中并行建设其他技术栈；确有阻塞时必须先记录原因再变更技术决策。
- 不为了小程序审核临时增加支付、商城、社区、聊天、分享裂变或与核心答题无关的能力。
- 不在首版强制收集手机号、微信头像、位置、通讯录或其他非必要个人信息。
- 不在判定口径未明确前接入外部 AI 判题模型。
- 不让小程序前端自行计算最终成绩、提交时间或排名。
- 不把测试学员数据带入正式公开榜单。
